# 角色素材优化推进方案（2026-09）

> 目标：把"角色是一坨会动的色块矩形"推进到"像样的角色"。先核实现状，再评估路线，最后给分期的落地方案。

---

## 一、现状核实（决定推进方式的三个事实）

1. **每个朝向只有一张静态图**：`PlaceholderArt.Character(key, color, dir, w, h, ppu)`
   画的是一个"矩形身体 + 头 + 朝向亮点"，没有走路帧、没有攻击帧、没有死亡帧。
   死亡表现是整张图变半透明（`EntityViewRegistry`）。
2. **取图入口只有一行**：`EntityViewRegistry.SpriteFor()` 里一句
   `PlaceholderArt.Character(...)` —— 这就是 README 里说的"换素材接入点"，确实是单点。
3. **管线里没有"帧"的概念**：`SpriteFor` 只按 `spriteId + 朝向` 取图，不按状态/时间取。
   **这是真正的瓶颈**：就算 8 向序列帧素材今天到手，现在的代码也只会显示其中一帧，
   走路照样是滑行的静止图。

**结论：第一步不是找素材，是把"帧"铺进管线。** 这一步纯代码、零风险，而且独立有价值
（程序动画让全部 100+ 实体立刻活起来）；素材到位后也只是往帧管线里填图。

---

## 二、路线评估（2026-09 重新查证）

| 路线 | 内容 | 成本 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 程序动画** | 不换图，把单帧升级成多帧程序动画（走路两帧摆动 / 攻击挥舞 / 死亡倒地） | 中 | 无 | **必做，第一期**。帧协议就是素材接入的前提 |
| **B. CC0 4 向行走图** | OGA 有 [CC0 Walk Cycles](https://opengameart.org/content/cc0-walk-cycles)（4 帧）、[4 Frame Walk Cycles](https://opengameart.org/content/4-frame-walk-cycles) 等纯 CC0 集 | 中 | **观感断层**：全是俯视像素风，和本项目 2:1 斜视 + 高分辨率占位风混排违和；8 向要靠镜像补（斜向动作失真） | 兜底。风格不匹配是硬伤 |
| **C. AI 生成 8 向序列帧** | 2026 已工具化：[PixelSprite](https://sprite.cocona.art/zh-CN)、[Pixel Forge](https://pixel-forge.net/rpg-character-sprite-generator) 等，传一张参考图出 4/8 向行走图集，"三周→八分钟" | 中（工具订阅 + 人工修帧） | 一致性要逐帧检查；**AI 生成物的商用条款按各工具确认**；帧与帧之间的细节抖动要人审 | **第二期试点**：先只做主角，验证违和度再决定批量 |
| **D. 外包/购买** | 传奇风格 8 向角色商城有售（itch / Unity Asset Store） | 大（按套几百~几千） | 钱和沟通成本；**注意识别扒原版传奇的素材**（和 CC0 铁律同一条线） | 暂不考虑，等 C 的试点结果 |

之前查证的结论仍然成立：**CC0 里没有现成的 8 向行走角色**（4 向的倒是有，但见 B 的观感问题）。

## 三、分期落地方案

### 第一期：帧管线 + 程序动画（纯代码，先让角色"活"起来）

**新增 `CharacterFrames` 接口（Unity 层）**，把"取哪张图"收口成一个协议：

```csharp
public enum CharState { Idle, Walk, Attack, Die }
public interface ICharFrames
{
    Sprite Get(string spriteId, Dir dir, CharState state, int frame, Color tint, int w, int h, float ppu);
}
```

- `EntityViewRegistry.SpriteFor` 改为按状态机取帧：
  - `Walk`：`e.Pos != 上一帧位置` 时触发，帧率 ~6.7 帧/秒（tick 驱动，和移动节拍一致）
  - `Attack`：`AttackSwing` 事件触发，占 2 帧、时长 = 出手间隔的一半（和 M6d 的攻速缩放一致）
  - `Die`：`EntityDied` 触发，倒地 2 帧 + 现有的半透明
  - 其余 = `Idle`（呼吸微缩放，便宜又有生命感）
- 默认实现 `PlaceholderFrames`：程序画帧——
  - 走路 = 身体左右两帧 + 脚部交替点
  - 攻击 = 身体朝 facing 前倾 + 武器亮线（复用 Slash 的形）
  - 死亡 = 压扁 40% + 灰化
- **一期验收**：不引入任何素材，肉眼看角色"走路在迈步、攻击在挥、死亡会倒"；
  无头 263+ 项全过；`SpriteFor` 不再直接调 `PlaceholderArt.Character`

成本：**中**（两三天）。这一期做完，二期素材接入就是"实现一个接口 + 填图"。

### 第二期：主角试点 AI 8 向（验证违和度，只做 1 个角色）

- 用 AI 工具给战士主角生成：8 向 × 4 帧行走 + 2 帧攻击（约 34 帧，32×48）
- 人工过一遍帧间一致性（轮廓跳动 > 1px 的修掉或重摇）
- 实现 `AiFrames : ICharFrames`，只对 `spriteId == "player"` 生效——**怪保持占位图**
  （混排正好能对比：如果主角和占位怪同屏不违和，才值得批量）
- 许可：确认工具的商用条款并把来源写进 `docs/素材来源`；AI 生成物按工具条款带免责说明
- **验收**：实际游戏里走两圈。违和 → 停，损失只有一次试点；和谐 → 进第三期

### 第三期：按试点结果二选一

- **和谐** → 批量生成 20 种怪 + 2 个 NPC（每个角色一次生成会话，风格用同一张参考图锁定），
  掉落光柱 / 品质色带 / 特效全部自动兼容（它们挂在帧管线之外）
- **违和** → 两个止损选项：
  a. 只保留主角新素材（"主角精修"在单机游戏里完全成立）；
  b. 转外包，按套采购传奇风格 8 向角色（先小套试水）

## 四、这条线上的两个纪律（沿用既定原则）

1. **不碰原版**：任何渠道的素材，只要是从传奇客户端扒的（爱给 / 500皮 / gmbbs 那类），一律不用。
   AI 生成物同样不带原版元素（不喂原版截图当参考图）。
2. **Domain 零改动**：帧状态机、素材加载全部在 Unity 层。`CharState` 的判定信号
   （位置变化 / AttackSwing / EntityDied）全是现成事件，Domain 不需要为表现新增任何东西。

## 五、成本汇总

| 期 | 内容 | 成本 | 产出 |
| --- | --- | --- | --- |
| 一 | 帧管线 + 程序动画 | 中（2~3 天） | 全部角色有走路/攻击/死亡动作；素材协议就位 |
| 二 | 主角 AI 8 向试点 | 中（1~2 天含修帧） | 违和度的真实答案 |
| 三 | 批量生成或止损 | 大（视结果） | 20 种怪 + NPC 换装，或只精修主角 |

先动第一期——它不需要任何外部资源，且无论后面选哪条路都用得上。
